# Учебник: делаем свой Instagram на FastAPI

> В этом учебнике **нет кода**, только понятия.
> Сначала читаем этап и понимаем идею. Потом говорим: «пиши код для этапа N».
> После каждого этапа проверяем всё в Swagger (`http://127.0.0.1:8000/docs`).
>
> Цель: на вопрос «какой код в проекте отвечает за чат / пост / историю / заметку / логин?»
> вы сможете ответить, в каком файле лежит этот код, что он делает и откуда что импортирует.

## Аналогия «Человек», которая проходит через весь учебник

| Этап аналогии | Что это в Instagram | Что пишем в коде |
|---|---|---|
| 1. **Человек появился** (родился, получил имя и паспорт) | Регистрация пользователя | Модель `User`, регистрация, вход, выход |
| 2. **У человека есть лицо и визитка** | Профиль (аватар, био) | Модель `Profile`, создаётся автоматически |
| 3. **Человек ходит и что-то делает** | Посты, истории, заметки | Действия пользователя (эндпоинты) |
| 4. **Человек знакомится с другими** (рукопожатие) | Подписки (follow) | Связь «пользователь ↔ пользователь» |
| 5. **Человек реагирует на других** | Лайки, комментарии | Связь «пользователь ↔ пост» |
| 6. **Человек разговаривает** (например, о погоде) | Чат / Direct | Сообщения, WebSocket |
| 7. **Человеку сообщают новости** | Уведомления | Модель `Notification` |
| 8. **Человек ищет знакомых** | Поиск | Поиск по username |

Каждый этап строится на предыдущем: нельзя разговаривать, если человек ещё не появился.

## Часть 0. Базовые понятия (прочитать обязательно)

### 0.1 Клиент и сервер
- **Клиент** — тот, кто просит: телефон, браузер, Swagger.
- **Сервер** — тот, кто отвечает. Это наше FastAPI-приложение.
- Аналогия: клиент — посетитель кафе, сервер — официант с кухней.

### 0.2 API и эндпоинт
- **API** — «меню» сервера: список того, что можно попросить.
- **Эндпоинт** — один пункт меню. Например, `POST /auth/register` значит «зарегистрируй меня».

### 0.3 HTTP-методы (что мы хотим сделать)
| Метод | Смысл | Пример |
|---|---|---|
| `GET` | получить, прочитать | посмотреть профиль |
| `POST` | создать | зарегистрироваться, создать пост |
| `PUT` / `PATCH` | изменить (целиком / частично) | изменить био |
| `DELETE` | удалить | удалить пост |

### 0.4 JSON
Формат, в котором клиент и сервер обмениваются данными: пары «ключ: значение».
Например, при регистрации клиент отправляет username, email и пароль, а сервер отвечает id и username нового пользователя.

### 0.5 Статус-коды ответа
| Код | Значение |
|---|---|
| 200 | всё хорошо |
| 201 | создано |
| 400 | ошибка в запросе (например, плохой пароль) |
| 401 | вы не вошли в систему (нет токена) |
| 403 | вошли, но вам сюда нельзя |
| 404 | не найдено |
| 409 | конфликт (например, такой username уже занят) |
| 422 | данные не прошли проверку (FastAPI делает это сам) |

### 0.6 База данных
- Место, где данные хранятся постоянно, как таблицы в Excel.
- Таблица = список однотипных вещей (пользователи, посты).
- Строка = одна вещь (один пользователь). Колонка = свойство (username, email).
- **id** — уникальный номер каждой строки, «номер паспорта».
- **Связь (ForeignKey)** — ссылка из одной таблицы на другую. Например, в посте хранится `user_id`, то есть кто автор.

### 0.7 Инструменты (библиотеки), которые будем использовать
| Библиотека | Зачем |
|---|---|
| **FastAPI** | сам веб-фреймворк: эндпоинты, Swagger |
| **Uvicorn** | сервер, который запускает FastAPI-приложение |
| **SQLAlchemy** | работа с базой данных через Python-классы (ORM) |
| **SQLite** | простая база данных в одном файле (встроена в Python) |
| **Pydantic** | проверка входящих и исходящих данных (схемы) |
| **passlib / bcrypt** | хеширование паролей |
| **python-jose / PyJWT** | создание и проверка JWT-токенов |
| **python-multipart** | загрузка файлов (фото, аватары) |

### 0.8 Модель и схема: важное различие
- **Модель (SQLAlchemy)** описывает, как данные **лежат в базе**. Например, у таблицы `users` есть колонка `hashed_password`.
- **Схема (Pydantic)** описывает, как данные **приходят и уходят через API**. Например, при регистрации приходит `password`, а в ответе пароля нет никогда.
- Аналогия: модель — это анкета в архиве, схема — бланк, который заполняют у окошка.

### 0.9 Структура проекта (папки и файлы)
```
instagram/
├── main.py              ← точка входа: создаёт приложение, подключает роутеры
├── database.py          ← подключение к базе данных
├── config.py            ← настройки (секретный ключ, время жизни токена)
├── models/              ← модели SQLAlchemy (таблицы)
│   ├── user.py
│   ├── profile.py
│   ├── post.py
│   └── ...
├── schemas/             ← схемы Pydantic (что приходит / уходит)
├── routers/             ← эндпоинты, сгруппированные по темам
│   ├── auth.py          ← регистрация, логин, логаут
│   ├── profiles.py
│   ├── posts.py
│   └── ...
├── services/            ← логика (хеширование, токены, отправка кодов)
├── dependencies.py      ← «кто сейчас вошёл» (текущий пользователь)
└── media/               ← загруженные фото
```
**Правило:** у каждой темы свой файл. Поэтому на вопрос «где код чата?» ответ всегда понятен: `models/message.py`, `schemas/message.py`, `routers/chat.py`.

### 0.10 Цепочка запроса (как ВСЁ работает)
```
Клиент (Swagger) → роутер (routers/...) → проверка данных (schemas/...)
 → логика (services/...) → база данных (models/...) → ответ JSON → клиент
```
Запомните эту цепочку: любой эндпоинт работает по ней.

## Этап 1. Человек появился: регистрация, вход, выход

### 1.1 Понятия
- **Регистрация (register)** — создание нового пользователя.
- **Вход (login)** — доказать, что вы это вы (логин + пароль), и получить «пропуск».
- **Выход (logout)** — сделать пропуск недействительным.
- **Хеширование пароля.** Пароль **никогда** не хранится как есть. Хранится «отпечаток» (хеш). При входе мы хешируем введённый пароль и сравниваем отпечатки. Даже если базу украдут, паролей там нет.
- **JWT-токен** — пропуск с подписью сервера. Клиент прикладывает его к каждому запросу в заголовке `Authorization: Bearer <токен>`.
  - **access-токен** живёт недолго (например, 30 минут), с ним ходим по API.
  - **refresh-токен** живёт долго (например, 7 дней), по нему получаем новый access.
- **Logout.** Refresh-токен хранится в базе; при выходе мы его удаляем или помечаем отозванным. После этого продлить сессию нельзя.
- **Подтверждение email / SMS.** После регистрации генерируем 6-значный код, «отправляем» его и ждём, когда пользователь его введёт.
  - В учебном проекте код **печатается в консоль** сервера: настоящие SMS платные (сервисы Twilio и подобные). Позже можно подключить реальную отправку.
  - У кода есть срок жизни (например, 10 минут) и ограничение попыток.

### 1.2 Данные пользователя (таблица `users`)
| Поле | Что это | Правила |
|---|---|---|
| id | номер | уникальный, ставится автоматически |
| username | ник (@ivan) | уникальный, латиница, цифры, `_` и `.` |
| email | почта | уникальная, правильный формат |
| phone | телефон | необязательный, уникальный |
| full_name | имя и фамилия | необязательное |
| hashed_password | хеш пароля | минимум 8 символов **до** хеширования |
| is_verified | подтверждён ли email/телефон | по умолчанию «нет» |
| is_active | активен ли аккаунт | по умолчанию «да» |
| created_at | дата регистрации | ставится автоматически |

Дополнительные таблицы:
- `verification_codes`: код, кому он, для чего (email/sms), когда истекает, сколько было попыток.
- `refresh_tokens`: токен, чей он, когда истекает, отозван ли.

### 1.3 Эндпоинты
| Метод и путь | Что делает |
|---|---|
| `POST /auth/register` | регистрация и отправка кода подтверждения |
| `POST /auth/verify` | ввод кода, после него `is_verified = да` |
| `POST /auth/resend-code` | отправить код ещё раз |
| `POST /auth/login` | вход по username/email и паролю, возвращает access- и refresh-токены |
| `POST /auth/refresh` | новый access-токен по refresh-токену |
| `POST /auth/logout` | отзывает refresh-токен |
| `GET /auth/me` | «кто я?»: данные текущего пользователя (нужен токен) |

### 1.4 Что проверить в Swagger
1. Зарегистрироваться и увидеть код в консоли.
2. Зарегистрироваться с тем же username и получить ошибку 409.
3. Ввести неверный код (ошибка), затем верный (успех).
4. Войти и получить токены.
5. Нажать кнопку **Authorize** в Swagger и вставить токен.
6. `GET /auth/me` с токеном вернёт ваши данные, без токена будет 401.
7. Сделать logout, затем `refresh` со старым токеном и получить ошибку.

- Где в проекте код регистрации? (`routers/auth.py`, `services/...`, `models/user.py`)

## Этап 2. Лицо и визитка: профиль

### 2.1 Понятия
- **Профиль** — публичная «визитка» пользователя. `User` отвечает за вход и безопасность, `Profile` — за то, что видят другие.
- **Связь один-к-одному:** у одного пользователя ровно один профиль.
- **Автоматическое создание.** В момент регистрации, в том же действии, создаётся пустой профиль. Пользователь его не создаёт сам.
- **Публичный / приватный аккаунт.** Приватный профиль видят только подписчики.
- **Загрузка файла (аватар).** Файл сохраняется в папку `media/`, а в базе хранится только путь к нему.

### 2.2 Данные профиля (таблица `profiles`)
| Поле | Что это |
|---|---|
| id | номер |
| user_id | чей профиль (ссылка на users) |
| bio | о себе (до 150 символов) |
| avatar | путь к фото |
| website | ссылка |
| is_private | приватный ли |
| счётчики | постов, подписчиков, подписок (считаются) |

### 2.3 Эндпоинты
| Метод и путь | Что делает |
|---|---|
| `GET /profiles/me` | мой профиль |
| `PATCH /profiles/me` | изменить био, сайт, приватность |
| `POST /profiles/me/avatar` | загрузить аватар |
| `GET /profiles/{username}` | посмотреть чужой профиль |
| `GET /profiles/{username}/posts` | посты этого человека (появится на этапе 3) |

### 2.4 Проверка
Зарегистрироваться, затем `GET /profiles/me`: профиль уже есть, хотя мы его не создавали. Изменить био, посмотреть чужой профиль.

## Этап 3. Человек что-то делает: посты, истории, заметки

### 3.1 Посты
- **Пост** — одно или несколько фото плюс подпись. Хранится навсегда, пока его не удалят.
- **Связь один-ко-многим:** у одного пользователя много постов.
- **Только автор** может изменить или удалить свой пост (иначе ошибка 403).
- **Пагинация** — отдаём посты порциями (например, по 10), а не все сразу.

| Метод и путь | Что делает |
|---|---|
| `POST /posts` | создать пост (фото и подпись) |
| `GET /posts/{id}` | один пост |
| `PATCH /posts/{id}` | изменить подпись (только автор) |
| `DELETE /posts/{id}` | удалить (только автор) |
| `GET /feed` | лента: посты тех, на кого я подписан (после этапа 4) |

### 3.2 Истории (Stories)
- Фото или видео, которое **живёт 24 часа**.
- У каждой истории есть `expires_at` (время создания + 24 часа). Если время прошло, история не показывается.
- **Просмотры:** кто посмотрел историю (таблица `story_views`).

| Метод и путь | Что делает |
|---|---|
| `POST /stories` | выложить историю |
| `GET /stories/feed` | активные истории тех, на кого подписан |
| `POST /stories/{id}/view` | отметить просмотр |
| `GET /stories/{id}/viewers` | кто посмотрел (только автор) |

### 3.3 Заметки (Notes)
- Короткий текст (до 60 символов) над аватаром в Direct, живёт 24 часа.
- У пользователя **одна** активная заметка: новая заменяет старую.

| Метод и путь | Что делает |
|---|---|
| `POST /notes` | поставить заметку |
| `DELETE /notes/me` | убрать заметку |
| `GET /notes` | заметки тех, на кого подписан |

## Этап 4. Рукопожатие: подписки (follow)

### 4.1 Понятия
- **Подписка** — связь «кто → на кого». Таблица `follows`: `follower_id` (кто подписался) и `following_id` (на кого).
- **Связь многие-ко-многим:** я подписан на многих, и на меня подписаны многие.
- Нельзя подписаться на себя и нельзя подписаться дважды.
- **Приватный аккаунт:** подписка сначала становится **запросом** и ждёт, пока её примут.

| Метод и путь | Что делает |
|---|---|
| `POST /users/{username}/follow` | подписаться (или отправить запрос) |
| `DELETE /users/{username}/follow` | отписаться |
| `GET /users/{username}/followers` | подписчики |
| `GET /users/{username}/following` | подписки |
| `GET /follow-requests` | входящие запросы |
| `POST /follow-requests/{id}/accept` | принять запрос |

После этого этапа заработает лента `/feed`.

## Этап 5. Реакция: лайки и комментарии

- **Лайк** — связь «пользователь ↔ пост». Один пользователь может поставить один лайк на пост. Повторный лайк ничего не меняет или снимает лайк.
- **Комментарий** — текст от пользователя к посту. Удалить комментарий может его автор или автор поста.
- **Ответы на комментарии** — у комментария есть `parent_id`, то есть на какой комментарий он отвечает.

| Метод и путь | Что делает |
|---|---|
| `POST /posts/{id}/like` | лайк |
| `DELETE /posts/{id}/like` | убрать лайк |
| `GET /posts/{id}/likes` | кто лайкнул |
| `POST /posts/{id}/comments` | написать комментарий |
| `GET /posts/{id}/comments` | список комментариев |
| `DELETE /comments/{id}` | удалить комментарий |

## Этап 6. Разговор: чат (Direct)

### 6.1 Понятия
- **Диалог (conversation)** — «комната», где общаются 2 и более человек. Таблица `conversations` и таблица участников.
- **Сообщение** — кто написал, в какой диалог, текст, время, прочитано ли.
- **Обычный HTTP** работает так: «спросил → получил ответ → соединение закрылось». Для чата этого мало: новое сообщение должно приходить **само**.
- **WebSocket** — соединение, которое остаётся открытым. Сервер сам «толкает» новое сообщение собеседнику.
  - Аналогия: HTTP — это письма, WebSocket — телефонный звонок.
- **Менеджер соединений** — список «кто сейчас онлайн и через какое соединение ему писать».

| Метод и путь | Что делает |
|---|---|
| `POST /chats` | начать диалог с пользователем |
| `GET /chats` | мои диалоги |
| `GET /chats/{id}/messages` | история сообщений |
| `POST /chats/{id}/messages` | отправить сообщение (через HTTP) |
| `WS /ws/chat` | живое соединение для мгновенных сообщений |

> WebSocket в Swagger не проверяется. Для него сделаем простую тестовую HTML-страницу или используем Postman.

## Этап 7. Новости для человека: уведомления

- Когда кто-то лайкнул пост, подписался или прокомментировал, создаётся запись в `notifications`: кому, от кого, тип, ссылка на объект, прочитано ли.
- Уведомления создаются **внутри** других действий. Например, код лайка заодно создаёт уведомление.

| Метод и путь | Что делает |
|---|---|
| `GET /notifications` | мои уведомления |
| `POST /notifications/read` | отметить прочитанными |

## Этап 8. Поиск

- Поиск пользователей по началу username или имени.
- Поиск постов по хештегам (`#travel`): хештеги из подписи сохраняются в отдельную таблицу.

| Метод и путь | Что делает |
|---|---|
| `GET /search/users?q=...` | найти людей |
| `GET /search/tags?q=...` | найти хештеги |
| `GET /tags/{tag}/posts` | посты по хештегу |
